## 2. Design: the hop limit

<!-- To prevent infinite data-plane forwarding loops in tunneled traffic, I modified the custom myTunnel header structure by adding an 8-bit hop_limit field and reducing the original dst_id field from 16 bits to 8 bits. This change compresses the overall header from an unaligned 32 bits into a clean, 32-bit (4-byte) structure arranged as hop_limit (8 bits), proto_id (16 bits), dst_id (8 bits). Reducing dst_id to 8 bits provides up to 256 unique tunnel exit destinations—which is more than sufficient for small-to-medium network topologies—while freeing up memory overhead to accommodate the hop limit counter without increasing the overall packet size. Ordering hop_limit before proto_id and dst_id mirrors standard IPv4 header design, where control metadata (like TTL) precedes destination routing information.

The host script (send.py) initializes the hop_limit with a default starting value of 64. This choice follows standard OS kernel defaults for IPv4 TTL, giving traffic sufficient headroom to cross normal multi-hop paths while ensuring looped packets drop quickly before exhausting network link capacity.

The hop limit is checked and decremented inside the ingress pipeline (MyIngress). Prior to applying the myTunnel_exact lookup, the pipeline checks if (hdr.myTunnel.hop_limit > 0). If valid, the switch decrements hdr.myTunnel.hop_limit = hdr.myTunnel.hop_limit - 1 and proceeds with tunnel forwarding. If hop_limit drops to 0, the check fails and the switch executes drop(), destroying the packet and breaking the loop.

To ensure end-to-end agreement across the path, tunnel.p4 (parser state parse_myTunnel, ingress logic, and deparser), send.py, and receive.py were all updated to match this 32-bit header definition. -->

## 5. Evaluation

<!-- a) Before running the mixed setup, I predicted a header mismatch. The new header is hop_limit (8 bits), proto_id (16) and dst_id (8), but the old one is only proto_id (16) and dst_id (16), so I expected s2 to misread it and drop the packet. Surprisingly, the packet still reached h2. Both switches read the EtherType 0x1212 the same way, and both headers are 4 bytes long, so s2 read the same tunnel bytes (3f 08 00 02 in the capture) but split them differently, proto_id 0x3f08 and dst_id 0x0002. The last two bytes are the low byte of my proto_id (0x0800) and my dst_id. Because that low byte is 0x00, s2 read them as dst_id 2 and its table matched. This was luck, if proto_id had a non-zero low byte, such as 0x0806, s2 would have read 0x0602 and dropped the packet. s2 never checks whether the header makes sense. Its parser just stopped at the tunnel header because 0x3f08 is not 0x0800, which is why the IP TTL stayed at 64, and its ingress only looks up dst_id. h2 received hop_limit 63, decremented once by s1. In the loop I also expected s2 to drop the packet, but for the same reason it kept forwarding it. s2 never decremented the hop limit, but s1 did on every visit, so the loop still ended at s1, s1 handled 64 packets (180 to 244) and s2 handled 63 (161 to 224), and the counts did not change 5 seconds later.

b) My mixed rollout showed the risk of a header change: the old switch forwarded my new header by luck instead of rejecting it. I compared two ways to roll out a change safely. The first is a new EtherType. New switches send the new header with EtherType 0x1213 and still accept the old 0x1212. An old switch does not recognise 0x1213, so its parser stops and the packet is dropped, just as the unknown EtherType was dropped in lab Step 3. This is safe and clear, because no switch can misread a header it doesn’t understand, but new-format traffic can only use paths where every switch has been upgraded. The second option is translation at the boundary. An upgraded switch converts the new header back to the old format before sending it to an old switch, using a port-to-version table filled in by the controller. Traffic keeps flowing during the upgrade, but the hop limit is lost on the old part of the path, so a loop made only of old switches is still unprotected, and every boundary switch needs extra logic. A third option is to order the fields so old switches still parse them, for example by adding hop_limit after proto_id and dst_id. The old switch then reads proto_id and dst_id correctly and forwards the packet, but it treats the extra byte as the start of IPv4, so it reads IPv4 one byte off and its checksum update corrupts the inner packet. This only works if the old program stops parsing after the tunnel header, so it is less safe than the other two options.

c) Control-plane loop checking, like check_paths() in Week 3, works before traffic flows, the controller checks the paths it has computed and can catch a loop or a broken path before any packet is affected. It can also catch problems a hop limit can’t, such as a path that never reaches its destination or delivers to the wrong host, because a hop limit only notices that a packet has travelled too far. But the controller can only check what it knows about. In C1 I created the loop myself with table_modify, directly on s2, so the controller never saw it, and it would also miss short-lived loops while rules are being updated or a switch that doesn’t apply its rules correctly. The hop limit works in the data plane while packets are moving, so it stops any loop, whatever caused it. However, it only reacts after the loop has already started. My packet still crossed the switches 64 times before it was dropped, and it was dropped silently without telling anyone. Real networks use both, the control plane prevents most loops in advance, and the data plane is the safety net that limits the damage when something slips through, in the same way IP uses a TTL even though routing protocols are designed to avoid loops.

d) I think the cost on a hardware switch would be small. A hardware P4 switch does not use a CPU for each packet. It runs the program in a fixed pipeline, and as long as the program fits, every packet is still processed at line rate. The hop limit only adds a small amount of parsing, one subtraction and a comparison with zero to the tunnel lookup that was already there, so I think it would fit easily. It also adds no bytes on the wire: the new header is the same 4 bytes as the old one, because I made dst_id 8 bits instead of 16. I think that is the real cost of the design: the tunnel can now address only 256 exits instead of 65,536. On a larger network I would keep dst_id at 16 bits and accept one extra byte per packet. In return, I think the hop limit saves bandwidth when something goes wrong, because a looping packet is dropped after 64 hops instead of using the links forever, as it did in C1. -->
